# 03. Multi-Agent Systems & Orchestration Prompts

Complex enterprise workflows exceed the context window, cognitive bandwidth, and tool capacity of a single agent. Multi-agent systems decompose tasks across specialized agents with isolated contexts and explicit communication protocols.

---

## 1. Multi-Agent Topology Taxonomy

```
A. Supervisor / Hierarchical          B. Multi-Agent Debate               C. Finite State Machine (Swarm)
         [Supervisor]                         [Agent A] <-------> [Agent B]          [Triage]
        /      |     \                             \           /                        |
    [Worker] [Worker] [Worker]                      [Judge / Synthesizer]             [Billing] <-> [Tech Support]
```

### 1. Supervisor-Worker Pattern
A centralized manager decomposes the user goal, dispatches sub-tasks to specialized workers, inspects results, and iterates until the goal is satisfied.

### 2. Multi-Agent Debate (Du et al., 2023; Liang et al., 2023)
Multiple agent instances with differing system personas or temperatures independently solve a problem, cross-examine each other's reasoning, and reach consensus. Demonstrably cuts factual hallucination in legal, financial, and medical tasks.

### 3. Peer-to-Peer State Machine (Swarm Pattern)
Agents execute atomic tasks and dynamically "hand off" control to another specialized agent by returning a function call: `handoff_to_billing(case_id)`.

## 2. Multi-Agent System Prompts

### A. Supervisor Orchestrator Prompt
```markdown
<system_identity>
You are the Engineering Incident Commander. You do not write code directly.
Your role is to orchestrate three specialized workers:
1. `log_analyst`: Queries Datadog/Elasticsearch and identifies stack traces.
2. `git_investigator`: Inspects recent GitHub pull requests and diffs.
3. `remediation_bot`: Prepares hotfix patches and restarts microservices.
</system_identity>

<protocol>
1. Evaluate current incident triage state.
2. Select exactly ONE worker to invoke next, or conclude if the incident is mitigated.
3. Output instructions to the worker in strict JSON:
{
  "next_agent": "log_analyst" | "git_investigator" | "remediation_bot" | "CONCLUDE",
  "task_directive": "Explicit instructions for what the agent must do",
  "context_summary": "Compact summary of facts gathered so far"
}
</protocol>
```

### B. Multi-Agent Debate & Cross-Examination Prompt
```markdown
<system_identity>
You are an Adversarial Security Reviewer. You are reviewing an architectural proposal generated by Agent Alpha.
Your objective is to find edge-case vulnerabilities, denial-of-service vectors, or authorization bypasses.
</system_identity>

<prior_agent_proposal>
{agent_alpha_proposal}
</prior_agent_proposal>

<review_directive>
1. Do NOT compliment or agree with the proposal.
2. Identify at least 3 concrete failure scenarios under high load or malicious actors.
3. For each failure scenario, provide a reproducible attack payload or condition.
4. Conclude with required architectural modifications.
</review_directive>
```

## 3. Mitigating Multi-Agent Pathologies

| Pathology | Symptoms | Architectural Prompt Defense |
| :--- | :--- | :--- |
| **Echo Chamber / Sycophancy** | Agents agree on flawed logic immediately | Enforce explicit devil's advocate role priors and separate system temperatures. |
| **Infinite Ping-Pong Chatter** | Agents exchange polite messages indefinitely | Hard cap conversation depth ($N \le 6$) and require an explicit `TERMINATION_SIGNAL`. |
| **Context Bloat & Token Runaway** | Message history grows exponentially | Require workers to return **state summaries** instead of dumping raw tool outputs into shared history. |
